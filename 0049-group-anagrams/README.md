# 49. Group Anagrams

🔗 https://leetcode.com/problems/group-anagrams/
📅 2026-08-02 · **Medium** · Arrays & Hashing (NeetCode 150)
⏱️ 약 9분, 자력 통과 (20분 타이머 내 → `solved`)

## 핵심 아이디어

애너그램이면 **정규화한 키가 같다** → 그 키로 그룹핑한다.
이 문제의 전부는 **무엇을 키로 삼을 것인가**.

---

## Big-O (제출한 풀이)

`n` = 문자열 개수, `k` = 문자열 최대 길이

| | 복잡도 | 근거 |
|---|---|---|
| **시간** | **O(n · k log k)** | 문자열마다 `sorted(s)` 가 `O(k log k)` — 이게 지배항. `join` `O(k)`, 딕셔너리 해싱 `O(k)`, 마지막 루프 `O(g)` (g = 그룹 수 ≤ n) |
| **공간** | **O(n · k)** | 키가 최대 n개이고 각 키 길이가 k → `O(n · k)`. 값은 원본 문자열 **참조**라 `O(n)` |

---

## 개선점 (다음 재도전 때 적용할 것)

### 1. 마지막 복사 루프는 불필요

```python
answer2 = []
for v in answer.values():
    answer2.append(v)
return answer2
```
→ `return list(answer.values())` 한 줄이면 된다. (4줄 → 1줄)

### 2. `if not answer.get(key)` 는 위험한 습관 ⚠️

- **의도**: "이 키가 있나?"
- **실제 동작**: "이 키의 **값이 truthy 한가**?"

이 문제에선 값이 항상 비어있지 않은 리스트라 우연히 맞는다.
하지만 값이 `0` · `""` · `[]` · `None` 일 수 있는 문제에서는 **바로 버그**가 된다.

- 키 존재 확인이면 → `if key not in answer:`
- 더 나은 건 `defaultdict(list)` → **if/else 자체가 사라진다**

### 3. 키를 바꾸면 정렬의 `log k` 가 사라진다 ⭐

제약이 **소문자 영문자**뿐이므로 26칸 카운트 배열을 키로 쓸 수 있다.

| 키 방식 | 문자열 1개 비용 | 전체 시간 |
|---|---|---|
| 정렬 `''.join(sorted(s))` | `O(k log k)` | `O(n · k log k)` ← 지금 |
| 26칸 카운트 튜플 | `O(k)` | **`O(n · k)`** |

---

## ⚠️ "실제로 더 빠른가" 는 다른 질문이다

같은 코드를 **8분 간격으로 두 번 제출**한 결과:

| 제출 | Runtime | Memory |
|---|---|---|
| 1차 (19:01) | 8 ms · Beats 92.10% | 22.01 MB · Beats 64.10% |
| 2차 (19:09) | **4 ms · Beats 99.34%** | **21.63 MB · Beats 97.45%** |

**코드는 한 글자도 안 바꿨다.**

- → LeetCode 의 Runtime/Memory **Beats % 는 최적화 지표로 쓸 수 없다.** 측정 노이즈가 알고리즘 차이보다 크다
- → 믿을 지표는 **점근 복잡도** 와 **코드 명료성** 두 가지뿐
- → `k` 가 작으면 C 로 구현된 `sorted` 가 카운트 키보다 실제로 빠를 수도 있다
- → 그래서 개선점 3 의 의미는 *"더 빠르다"* 가 아니라 **"면접에서 `log k` 를 제거할 수 있다고 말할 수 있다"**

> 🚨 `Beats 99.34%` 를 보고 "내 코드가 최적이다" 라고 결론내면 위 개선점 1~3 을 영영 못 본다.

## 배운 것

- `defaultdict(list)` — Arrays & Hashing 카테고리 내내 쓰인다. 손에 붙일 것
- `dict.get()` 으로 **키 존재**를 검사하지 말 것 (truthy 검사임)
- **키 설계가 곧 복잡도** — 같은 그룹을 만드는 키 함수가 여러 개 있고, 어떤 걸 고르냐로 `log k` 가 붙었다 떨어진다
- 벤치마크 숫자와 실제 개선을 혼동하지 말 것
